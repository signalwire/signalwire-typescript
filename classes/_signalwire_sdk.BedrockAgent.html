    Class BedrockAgent

    Agent implementation for the Amazon Bedrock voice-to-voice model.

    Supports all standard agent features (prompt building with text and POM, skills and SWAIG functions, post-prompt, dynamic configuration) but renders SWML with the amazon_bedrock verb rather than ai.

    Example

    import { BedrockAgent } from '@signalwire/sdk';

    const agent = new BedrockAgent({
      systemPrompt: 'You are a helpful voice assistant.',
      voiceId: 'tiffany',
    });

    agent.setInferenceParams(0.5, 0.95, 2048);
    await agent.serve({ port: 3000 });

    addPerCallConfig

    • addPerCallConfig(cb: DynamicConfigCallback): this

      Register a per-request configuration callback, keeping any already set.

      Same signature and contract as setDynamicConfigCallback, except that callbacks accumulate instead of replacing each other. They run in registration order on the same per-request copy, so a later one sees what an earlier one configured. This is the composable form: a base class and a subclass, or an agent and a helper, can each register what they own without knowing about each other. setDynamicConfigCallback replaces every callback registered so far.

      Rejecting a call: a callback can't refuse the request, but it can decide what the call does. Build the agent to fail closed, with addPostAnswerVerb('play', { url: 'say:...' }) and addPostAnswerVerb('hangup', {}) and no tools, so the call hears the message and hangs up before the ai verb runs. For a call the callback accepts, add the tools to agent and call agent.clearPostAnswerVerbs() last. A callback that throws is logged and the copy is rendered as it stands, so a failure before that last step leaves the goodbye in place. A callback that throws stops the ones after it but doesn't restore verbs an earlier one cleared, so the callback that clears them must run last. Callbacks run for every request of the call (the SWML fetch, each tool call, the summary), and only the SWML fetch carries the caller's data (such as userVariables): verify there, remember the call_id, and check it on later requests. See "Rejecting a Call" in docs/agent-guide.md.

      Parameters

      • cb: DynamicConfigCallback

        Callback receiving (queryParams, bodyParams, headers, agent), where agent is the per-request copy. Configure that, never the agent itself, or the configuration leaks across callers. May be async.

      Register a handler that runs when the call starts, before the AI speaks.

      Handlers run in registration order with rawData, the whole SWAIG request (call_id, global_data, the caller's details). This wraps the platform's reserved startup_hook function, the counterpart of the hangup_hook behind onCallEnd. The platform calls it once, after the call is answered and before the AI's first turn, and never offers it to the model.

      The platform waits for the hook before the AI starts, so a slow handler delays the greeting; it waits up to 120 seconds for a function's reply and sends the request again after a timeout or a 5xx. Keep handlers short; start long work without awaiting it and send its result into the call later (calling.aiMessage() on the REST client). Like any function request, the hook's request can be sent again after a timeout or an error, so make handlers safe to run twice.

      A handler may return a FunctionResult, or nothing. What the platform does with the hook's reply:

      • its actions run at once, in registration order across handlers (for example updateGlobalData() to give the call data before the conversation starts);

      postProcess isn't used: the combined result runs its actions at once. The platform adds every hook reply to the conversation, so a hook whose handlers return no text still adds a short placeholder line, as any function with an empty reply does.
