# API reference

The TypeScript SDK's API reference, generated by TypeDoc from the TSDoc
comments in `src/`, with the SignalWire docs navbar on every page, published
as a single unversioned site to this repo's own GitHub Pages:

> https://signalwire.github.io/signalwire-typescript/

## Layout

```
reference/
  typedoc.json        TypeDoc config: entry points, strict validation, `out`
  typedoc-navbar.css  TypeDoc layout for the navbar: toolbar and sidebar offsets
  typedoc-navbar.js   theme adapter: the navbar's theme control drives TypeDoc's
  navbar/             the navbar; generator-agnostic, see navbar/README.md
  _site/              the built site                                [gitignored]
  README.md           this file
```

## Build

```bash
npm run docs:reference
```

Runs TypeDoc over the package exports (`src/index.ts`, `src/livewire/index.ts`)
into `reference/_site`, then `scripts/inject-navbar.ts`, which copies the navbar
into the site and adds it to every page. Every TypeDoc warning fails the build
(`treatWarningsAsErrors`): a stale `@param`, a link that does not resolve, or a
link to a symbol the package does not export. Missing comments do not fail it;
the doc-coverage floor in `scripts/run-ci.sh` tracks those. The navbar step
exits 1 on a page it cannot edit.

Every path in the generated pages is relative, so the site works under the
`/signalwire-typescript/` base path.

## CI

Two workflows.

`.github/workflows/reference-check.yml` builds on every PR touching `src/`,
`reference/`, the package files, or `tsconfig.json`. Build only: `contents:
read`, never deploys.

`.github/workflows/reference-docs.yml` builds and publishes. It runs the same
build, stamps `version.txt`, and only then deploys with
[ghp-import](https://github.com/c-w/ghp-import), the tool `mkdocs gh-deploy`
wraps, so the TypeScript and Python sites are published the same way.

- **Triggers:** a reusable `workflow_call` from `publish.yml`, which invokes it
  after the CI gates and `npm publish` have succeeded, plus `workflow_dispatch`
  for manual and fork-preview runs. There is deliberately no `release:
  published` trigger: that release is created with `GITHUB_TOKEN`, and GitHub
  raises no workflow-triggering events for that token, so the trigger would look
  right and never fire on the normal tag path.
- **Publishes only when** the run is on `signalwire/signalwire-typescript` (not
  a fork), the tag is stable semver (`vX.Y.Z`) so an rc tag cannot overwrite the
  stable site, and the tag is at least as new as the version recorded in
  `version.txt` at the root of the live site. Anything the gate cannot
  positively determine, such as an unreadable `gh-pages` or a site with no
  marker, fails closed rather than publishing, and fails the job so the run goes
  red. The npm publish is already done by then and is not affected; "Re-run
  failed jobs" republishes once the cause is repaired.
- A `workflow_dispatch` run builds a preview, and publishes only if you tick the
  `deploy` input **and** dispatch from the default branch. Without that second
  condition any branch in the dropdown could publish itself as the official
  public reference, running its own code under a `contents: write` token.
- **On rollback:** ghp-import replaces the whole site tree on every deploy but
  does not discard history. Run without `--no-history`, it parents each deploy
  onto `origin/gh-pages`, and the push is a plain fast-forward. A bad publish is
  recoverable by hand with
  `git fetch origin gh-pages && git push --force origin origin/gh-pages~1:gh-pages`.
  The gate exists because that recovery depends on somebody noticing, not
  because rollback is impossible. This is also why the gate's fetch of
  `gh-pages` must stay: it is what gives ghp-import `origin/gh-pages` to parent
  on, and without it the push lands a parentless orphan and the history really
  is gone.
- **After the push,** the job compares commits and fails unless a new
  `gh-pages` commit exists, the remote is at it, it parents on the previous
  deploy, and it carries the marker this run stamped. ghp-import's exit code is
  not proof: if its `git fast-import` fails it still pushes, and pushing the
  unchanged branch succeeds with nothing to do. Nor is the marker alone: on a
  re-run or a marker-preserving dispatch the old site already carries it.
- **Two publishes at once:** publishing runs queue behind each other, but
  GitHub keeps only one pending run per group and cancels the older one when
  another queues. Two release tags within one docs job of each other, or a
  dispatch deploy during a release, drop one publish as cancelled, not failed.
  If the dropped one was the newest version, re-run its `reference-docs` job;
  the gate publishes it unless the live site is already newer.

## Going live

Two one-time steps, in this order. The Pages dropdown cannot offer `gh-pages`
until the branch exists, so the dispatch has to come first.

1. Run `reference-docs` manually from the default branch with the `deploy` input
   ticked and `version_marker` set to the release the default branch is at, as
   `package.json` has it (`v3.7.1` at the time of writing). That creates
   `gh-pages` with the current reference and a marker the gate can compare the
   next release against. Leave `version_marker` blank only if the default branch
   has unreleased API changes: the site is then stamped with the `v0.0.0` floor
   until the next release replaces it.
2. In the GitHub UI: **Settings > Pages > Build and deployment >
   Source = "Deploy from a branch", Branch = `gh-pages` / `(root)`.**

Pages then serves the site at `https://signalwire.github.io/signalwire-typescript/`.
Every later stable release republishes it with its own tag.

### The version marker

`version.txt` at the site root records the version currently published, and the
monotonicity check reads it. **Every** publish stamps it, dispatches included:
ghp-import replaces the whole site tree, so a dispatch that did not re-stamp
would erase the marker and silently disarm the guard for the next release. A
dispatch preserves whatever is already there, and publishes the default
branch's reference under it. To put the released content back afterwards,
re-run the `reference-docs` job of the last release's publish run: the gate
accepts an equal version.

A site with no readable marker, or one that is not `vX.Y.Z`, is therefore an
anomaly, and the gate refuses to publish over it on both paths: a release
fails, and a dispatch fails unless the `version_marker` input is set. The
`v0.0.0` floor applies only when `gh-pages` does not exist yet. If the marker
ever needs repairing, for instance after a typo tag like `v31.0.0` sorts newest
and starts blocking real releases, dispatch a publish with the `version_marker`
input set to the correct `vX.Y.Z`.

### `.nojekyll`

TypeDoc names module pages with a leading underscore
(`interfaces/_signalwire_sdk.*.html`), which Jekyll would exclude. TypeDoc
writes `.nojekyll` into the site, and the deploy passes `--no-jekyll` as well,
so the file is always at the site root.
